# 0013 -- The 1.0.1 audit fixes: PeakEWMA design, eligibility ownership, the Pool contract, per-bin CHBL

- Status: Accepted
- Package: @zakkster/lite-pick 1.0.1 (bug-fix release)
- Builds on: ADR 0001 (selection-kernel boundary), ADR 0002 (anti-flapping), ADR 0004 (SmoothWRR sole-writer weight state), ADR 0007 (the /pool adapter), ADR 0009 (PeakEWMA), ADR 0011 (BoundedLoad / CHBL).
- Date: 2026-09-27

## Context

A full external audit (`audit/2026-09-26/`, audited code state commit `8c1ecc7` = version 1.0.0) read
`Pick.js` and `Pool.js` line by line and reproduced every behavioural claim against the real modules.
It found 6 High, 17 Medium and 26 Low items. Before fixing, H1-H4 and M1 were INDEPENDENTLY reproduced
here on darwin/arm64 Node 26 (the audit itself ran on Linux / Node 22). 1.0.1 fixes H1-H4, M1-M4, the
`verify`/gate items (H5, H6, M-T1..M-T4), the type items (L15, L16, L5, L6), the doc items (M-Doc1,
etc.), and the demo items (M-D1..M-D4). This ADR records the DESIGN decisions behind the caller-visible
fixes; the mechanical fixes (index validation helper, the CI workflow, the tarball check) are in the
CHANGELOG. None of these are new features, so they ship as a PATCH (see "Semver" below).

## Fork 1 -- Eligibility ownership: setEligible is the ONLY writer; the Eligibility object waits for 2.0 (H2)

- Root cause of H2: `BalancerBase` caches `_live` at construction and maintains it only in
  `setEligible`; `SmoothWRRBalancer` likewise caches `_totalEligibleWeight`. Every `pick()` depends on
  those caches (the fail-closed `_live === 0` short-circuit, the P2C/PeakEWMA `_live === 1` shortcut,
  SmoothWRR's `cur[best] -= total`). A DIRECT write to the shared `eligible` bitmap, or one array
  SHARED across balancers, desyncs the cache: a pool that is up but picks nothing, weight ratios
  destroyed, or 100% of traffic onto one node -- all reproduced.
- 1.0.0's RECIPES endorsed a direct `eligible[i] = 0` write ("zero-copy, pick sees it live") and reused
  one array across balancers. That guidance is REMOVED.
- Ratified CONTRACT (1.0.1): `setEligible()` is the ONLY supported writer of the eligibility view, and
  EACH balancer needs its OWN array. This is the minimal, non-breaking fix -- it changes documentation
  and adds validation, not the constructor signature. SmoothWRR's `pick` carries a comment that its
  `best >= 0` guarantee holds only under this contract.
- REJECTED for 1.0.1: dropping the `_live` cache (compute liveness during the scan). It would slow the
  O(1) strategies and is a larger change than a patch warrants.
- DEFERRED to 2.0: the `Eligibility` object (audit RECOMMENDATIONS section 3.1) -- a small class owning
  the bitmap, `live` and an `epoch`, so there is no per-balancer cache to desync and an array is
  truly shareable. It is the right long-term model but it CHANGES the constructor shape (a shared unit
  instead of a raw `Uint8Array`), so it is a breaking change and cannot ride a patch. Kept out of
  1.0.1 deliberately.

## Fork 2 -- PeakEWMA cost function: three cases, a lifetime-mean baseline, and a busy floor (H1)

The 1.0.0 cost was `(inflight + 1) x ewmaAt(now)` with an unsampled node reading a fixed 1.0 ns
baseline. Two failures combined into a black hole: (a) an unsampled node's cost `(inflight+1) x 1` beat
a sampled node's `1 x 1e6` until it held ~1e6 requests in flight, and (b) Pool only called `recordRtt`
on SUCCESS, so a fast-failing or hung node was never sampled and kept the 1.0 baseline forever.

Ratified 1.0.1 cost, per candidate (still a pure read, scalar-only, 0 B/op in the both-sampled steady
state):

- **unsampled AND idle (`inflight === 0`) -> 0.** An idle cold node is the cheapest, so it gets the
  next request -- graceful least-connections. This is NOT a kernel-enforced one-shot probe: an idle
  unsampled node costs 0 EVERY time it is idle, so it naturally holds exactly one request in flight at
  a time (the next pick sees `inflight > 0`) until its first `recordRtt`.
- **unsampled AND busy (`inflight > 0`) -> `(inflight + 1) x mean`,** where `mean` is the pool's
  LIFETIME mean sampled rtt (`_samp[0] / _samp[1]` = running sum / count, or 1.0 before ANY sample). A
  cold-but-busy node is priced at what the pool actually costs, not the old 1.0 ns.
- **sampled -> `(inflight + 1) x base`, `base = max(decayedEWMA, dt)` WHILE BUSY else `decayedEWMA`**
  (`decayedEWMA = ewma x exp(-dt/tau)`, `dt = max(now - stamp, 0)`). The busy FLOOR is the key: a hung
  node has `inflight > 0` and no completion, so `dt` grows without bound and its cost grows with it,
  instead of decaying toward 0 and becoming the most attractive pick.

Why the lifetime-mean baseline for the unsampled-busy case, and not the rejected alternatives:

- REJECTED `initialRttNs` constructor option: it is a magic number the caller must guess. The pool's
  own lifetime mean is self-calibrating and needs no tuning.
- REJECTED a `pending + 1` multiplier ALONE (Finagle's pending penalty) with no baseline change: the
  multiplier scales the baseline, so with a 1.0 ns baseline a busy unsampled node is still far cheaper
  than a sampled one. The multiplier is necessary but not sufficient; the baseline had to move.
- The lifetime mean saturates to `+Infinity` past ~1.8e308 of summed rtt and STAYS Infinity (a
  cold-but-busy node then prices at Infinity) -- never NaN. It is maintained in a pre-allocated
  `Float64Array(2)` (sum, count), per the hot-path law (no per-op object).

ACCEPTED CAVEAT (a 1.1.0 refinement): a node that was idle and then takes a request is priced by
time-since-its-LAST-response (the `dt` floor / the mean) until that in-flight request completes, so a
node that has just started a fresh (not hung) request is over-priced. The exact fix is a per-dispatch
"busy since" stamp, which is a 1.1.0 item; the lifetime mean also never forgets a latency-regime change
(a decaying mean is 1.1.0). These are disclosed, not silent.

Also folded in: `dt` clamped `>= 0` in `pick`, `recordRtt` and `ewmaAt` (L6, a non-monotonic clock can
no longer inflate via `exp(+x)`); `tau` is documented as the EWMA TIME CONSTANT with half-life
`tau x ln2` (L5, no math change).

## Fork 3 -- Pool failure penalty and re-probe cadence (H1, Pool side)

- A thrown attempt now feeds `recordRtt(i, max(elapsed, failurePenaltyNs), done)`. `failurePenaltyNs`
  is a new `opts.failurePenaltyNs` (default `1e9` = 1 s, validated finite `> 0`). So the kernel's
  new cost function has the failure DATA it needs -- the black hole is closed on both sides.
- Measured (4 PeakEWMA nodes, node 0 always throws): failure rate 49.4% (988/2000) in 1.0.0 ->
  ~0.05% (1/2000) over a short run; a hung node took 1 dispatch (was 4891/10000).
- RECOVERY is intentional, not a leak: at `tau = 30 ms` the penalized node's estimate decays back to
  competitive after roughly `tauNs x ln(failurePenaltyNs / healthyRttNs)`, so it is RE-PROBED at that
  cadence (~107 requests; measured cadence 2.14e8 ns vs 2.07e8 ns predicted; steady-state share
  ~0.95%). A node that has recovered is picked again; a node that is still failing is re-penalized.

## Fork 4 -- BoundedLoad per-bin capacity, NOT HAProxy's global budget (H4)

- 1.0.0 used `cap = (1 + eps) x total / live` with no ceiling. Whenever `total < live / (1+eps)` the
  cap fell below 1, so ANY backend with a single request in flight counted as over cap and a same-key
  request was scattered -- exactly at low load, where cache affinity matters most.
- Ratified: `cap = ceil((1 + eps) x (total + 1) / live)`. The `+ 1` counts the INCOMING request -- the
  Mirrokni-Thorup-Zadimoghaddam PER-BIN capacity -- so the cap is always `>= 1`. The `Math.ceil`
  matches the paper's integer capacity but is a no-op for the integer `inflight < cap` test
  (`inf < ceil(x)` == `inf < x` for integer `inf`), so at `n = 10`, `eps = 0.25` old and new behave
  identically for `total <= 7`; the ONLY difference is the boundary where the old cap was exactly 1.0
  (`total = 8`) and evicted a load-1 home.
- The audit's literal low-load repro (a 2nd concurrent same-key request overflows at `total = 1`) is
  CORRECT per-bin-capacity behaviour, not a bug: with one request already home and one incoming,
  `(1+eps)(1+1)/live = 2.5/10 = 0.25`, ceil 1, and the home already holds 1, so `1 < 1` is false and it
  overflows. Low-load stickiness is a matter of choosing a larger `eps`, not of the formula.
- REJECTED: HAProxy's `hash-balance-factor` definition. It is NOT the same: HAProxy splits ONE global
  `ceil((m+1) x F / 100)` slot budget across servers by weight (min 1), which is STRICTER -- at
  `total = 8` / `n = 10` it would move the load-1 home that per-bin capacity keeps. Per-bin capacity is
  the paper's definition and the one the roadmap cited; we keep it.

## Fork 5 -- The Pool contract: distinct failover, required channels, loud feedback (M2, M3, M4)

- **M2 (distinct failover).** 1.0.0 just re-picked with the failed node's in-flight raised, which for a
  keyed or deterministic strategy returns the SAME backend. 1.0.1 tracks a per-run tried set, re-picks
  up to `REPICK_LIMIT` (8) while the strategy repeats a tried endpoint, then scans for an eligible
  UNTRIED endpoint from a key-derived start (keyed: stable per key, spread across keys so one failing
  backend does not funnel every key onto one neighbour) or a rotating per-Pool cursor (unkeyed).
  Ratified boundary: when NO untried eligible endpoint remains, failover STOPS and the last error is
  thrown. Pool owns SPATIAL failover, not temporal retry (ADR 0007), so a 1-node pool with `tries: 3`
  makes 1 attempt -- it must not re-dispatch to an endpoint that already failed this run.
  ConsistentHash keyed `tries: 3` now hits 3 distinct backends (was `3, 3, 3`); a failing backend's
  keys spread over neighbours (max share ~23%).
- **M3 (separate, required channels).** Keyed balancers carry `static KEYED = true`
  (`ConsistentHashBalancer`, inherited by `BoundedLoadBalancer`) and latency balancers carry
  `static LATENCY = true` (`PeakEwmaBalancer`). Pool reads these markers off `balancer.constructor`
  (duck-typed, imports nothing new) and REQUIRES a numeric `opts.key` for a keyed balancer
  (`LITE_PICK_KEY_REQUIRED`) and an `opts.clock` for a latency balancer (`LITE_PICK_CLOCK_REQUIRED`).
  The key reaches ONLY a keyed pick; a clock reading NEVER reaches a keyed pick. A non-keyed CLOCKED
  run still passes the clock reading to `pick(now)`, preserving 1.0.0 behaviour for a duck-typed
  latency balancer that omits the marker. This kills the 1.0.0 foot-gun where a missing key routed
  everything to backend 0 and where `key` and `clock` were conflated onto one `pick` argument.
- **M4 (loud, single-shot feedback).** Success-time `recordRtt` moved OUTSIDE the attempt's try/catch,
  so `fn` runs exactly once; if it fails, `run` rejects with `LITE_PICK_FEEDBACK` carrying `.cause`
  (the feedback error) AND `.result` (fn's resolved value -- the caller loses nothing). If PENALTY
  feedback after a failure fails, `run` throws fn's ORIGINAL error object (identity preserved) with a
  non-enumerable `liteFeedbackError` attached, and stops failover. A non-finite clock reading throws
  BEFORE dispatch; a backwards but finite reading records NO sample (a fabricated 0 ns rtt would make
  the node look instant), while `done === now` is a real coarse-clock 0 and IS recorded. The abort
  signal is checked before EVERY attempt (an already-aborted signal dispatches nothing), including a
  structural `{ aborted: true }` signal with no `throwIfAborted`. `run(fn, null)` is valid (L1). A
  throwing custom `note(+1)` no longer leaves an unpaired `note(-1)` at settle. `liteQueryFetcher`
  forwards `clock` and `failurePenaltyNs`.

## Semver -- why these are patch fixes, and why M5 was moved to 1.1.0

- 1.0.1 is a PATCH. Every change either fixes a behaviour that contradicted its own documented contract
  (H2 eligibility, H3 weight-0, H4 stickiness, M1 validation, M2 "distinct" failover, M4 double-run) or
  hardens a contract that was already the intent (M3 required key/clock, the abort-before-dispatch
  check). No public class, method or constructor signature is removed or has a required parameter added
  at the JS level. `opts.failurePenaltyNs` is additive with a default. The `.d.ts` tightening
  (`pick(now)` / `pick(keyHash)` required on the CONCRETE classes) reflects the always-true runtime
  requirement; `BalancerBase.pick` stays loose so subclasses remain assignable.
- **M5 (LeastConn/NQ tie order) is explicitly NOT fixed in 1.0.1.** 1.0.0 DOCUMENTED "lowest index" as
  the tie-break, so a rotating tie-break is a change to a promised behaviour, not a bug fix -- it does
  not belong in a patch. 1.0.1 instead documents the tie order as UNSPECIFIED; the rotating tie-break
  lands in 1.1.0.

## The realistic-argument boxing limitation and the open recordRtt item

- Disclosed, shipped, fixed in 1.1.0: V8 boxes a `HeapNumber` (~16 B) for a number argument that is not
  a small integer when the call is not inlined -- `PeakEWMA` `pick(now ~1.7e15)`, `recordRtt` with a
  realistic clock + fractional sample (~16-30 B), and `ConsistentHash`/`BoundedLoad`
  `pick(keyHash >= 2^31)` (~16 B). Small-integer arguments are 0 B/op (`< 2^31` on stock 64-bit Node,
  `< 2^30` on pointer-compressed builds; values from `%` or division may box even when small). The
  1.1.0 plan: buffer-based `xxxFrom(buf, i)` variants that read the clock/key from a caller-owned typed
  array (prototype measured 0 B/op at 1e15), per the zero-box law. `test:perf` prints these as
  report-only lines every run so the limitation is measured, not merely asserted.
- OPEN (root cause NOT established, tracked for 1.1.0): run in isolation with some integer sample
  patterns (mod 500000, step 1000), the PerfGate `recordRtt` lane shows a small allocation that scales
  with window length (8N: 2, 16N: 4, 32N: 9 scavenges at the 1 MB pin); it disappears with
  `--no-maglev`, `--no-concurrent-recompilation`, or a preceding lane. Printed as a report-only line.

## Consequences

- Correct under every DOCUMENTED usage: no strategy can pick a weight-0 or down node, PeakEWMA + Pool
  cannot be black-holed, a MARKED keyed balancer cannot silently collapse onto one backend, and a
  feedback error cannot re-run `fn` or be swallowed. (Correction, audit 2026-09-29: 1.0.1 shipped two
  Pool regressions -- an UNMARKED keyed balancer lost `opts.key` and collapsed onto one backend (N2),
  and a caller abort fed the 1 s penalty (N1). Both are fixed in 1.0.2. The RECIPES section 8 manual
  loop still taught the black hole until 1.0.2 (D1).)
- `Pick.js` is no longer a pure STRATEGY-APPEND diff (as prior releases were): the eligibility contract,
  the PeakEWMA cost function, the CHBL cap and the shared index-validation helper touch existing
  classes. That is expected for an audit-fix release and is why it is documented here rather than as a
  new-strategy ADR.
- The new tests target these exact regressions. (Correction, audit 2026-09-29 D2: an earlier wording
  said "a revert-check runs each new gate against `git show HEAD:<file>`". No such script exists; only
  the soak teeth use `git show`. Mutant checks are done by hand per change, and audit 2026-09-29 found
  one test that a mutant survived -- SmoothWRR A5, fixed in 1.0.2 as A5b.)
- Not addressed here (later releases): the soak redesign (audit RECOMMENDATIONS section 1),
  observability (section 2), and the `Eligibility` object (Fork 1, deferred to 2.0).

## Deferred from the 2026-09-26 audit (recorded 2026-10-03, audit 2026-09-29)

1.0.1 left these Low items unfixed without saying so; they are deferred to 1.1.0 explicitly here. None
can return a down or weight-0 node, so none is a correctness bug under the documented contract.

| Item | What | Plan (1.1.0) |
|---|---|---|
| L2 | The sparse-eligibility fallback scan (P2C `_draw`, WeightedRandom) is biased: with 2 of 100 nodes eligible the split is 63.5/36.5, and the code comments call it "unbiased". | Uniform choice among eligible nodes on the fallback; fix the comments either way. |
| L3 | ConsistentHash / BoundedLoad fail closed after a 64-SLOT probe window: with 60 of 64 backends down, ~1% of keys get `PICK_NONE` although 4 are healthy. Documented, but an availability loss in mass outages. | A cold O(M) table sweep when the window is exhausted. |
| L4 | The PeakEWMA blend weights history by `w^2` (`ewma w^2 + s (1 - w)`) where Finagle uses `cost w + s (1 - w)`. | Use the Finagle blend, or document the difference with measured effect. |
| L7 | ConsistentHash `M` has no upper bound; above ~9.5e7 the permutation arithmetic exceeds 2^53 and `_build` could spin. | Cap `M` (<= 2^24 + prime) and use additive modular stepping. |
| L8 | The `nextBelow` comment says "multiply-shift"; the code is float division (bias negligible). | Fix the comment. |

Also deferred to 1.1.0 from the 2026-09-29 audit: N4 (the "larger eps buys stickiness" wording), N5
(a hung, never-sampled node has no time-based cost floor), N6 (keyed failover gives the failed
backend's neighbour a double share), alongside the already-deferred M5 and L14.
