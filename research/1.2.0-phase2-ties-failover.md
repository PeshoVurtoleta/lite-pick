# 1.2.0 phase 2 -- tie-breaking (K3) and /pool failover (K10 + weight 0)

Status: RESEARCH, written 2026-10-11 before any phase-2 code. Decisions marked DECIDE are the user's.
Evidence was reproduced in-repo on 1bc5eec (scripts: `$scratch/r120p2/repro/`, seeded xorshift32, ten seeds
per cell). Prior art was read from primary source files where reachable; anything not confirmed from a
primary source says so.

## 0. One-paragraph summary

All three findings are real. K10 and the weight-0 failover bug reproduce exactly. K3 reproduces in
DIRECTION but not in the audit's magnitude, and it is NOT NQ-only: SED shows the largest positional bias
(the first weight-1 node gets ~17% more than the last, relative), and LeastConn has a small one too. The
standard fixes exist in shipped code: Envoy's least-request FULL_SCAN does exactly the reservoir tie-break
the audit proposed, and Envoy's Maglev and Linux IPVS's Maglev scheduler fail over by re-hashing per attempt
(never a linear neighbour walk) while re-checking weight/availability on every probe. Recommendation: adopt
both, with the gates in section 6.

## 1. Evidence (in-repo)

### 1.1 K3 -- positional bias in the least-connection family

Discrete-event simulation: Poisson arrivals at load 0.9, exponential service, 8 nodes, 2e6 measured
arrivals x 10 seeds per cell; seed-to-seed sd of a node's share ~0.02 pp. Models: (a) equal service rates;
(b) service rate = weight; (c) weight-many parallel slots of rate 1. The audit's generator is unknown; its
weight-4 shares (~20%) fit (b) or (c).

Model (b), weights `[1,1,1,1,4,4,4,4]` (share %, nodes 0..7):

| strategy  | w1 group                  | w4 group                      | worst within-group gap |
|-----------|---------------------------|-------------------------------|------------------------|
| NQ        | 5.15 5.14 5.13 5.13       | 19.95 19.88 19.83 19.79       | 0.16 pp (0.8% rel.)    |
| SED       | **3.66 3.49 3.31 3.14**   | 21.61 21.60 21.60 21.59       | **0.52 pp (17% rel.)** |
| LeastConn | 5.46 5.45 5.44 5.45       | 19.44 19.55 19.60 19.62       | 0.18 pp (0.9% rel.)    |

- The gradient FOLLOWS POSITION: reversing the layout (`[4,4,4,4,1,1,1,1]`) reverses it, and the interleaved
  layout `[1,4,1,4,...]` is flat. Model (a) shows the same shape (SED w1 group 11.45 -> 10.76 = 0.69 pp).
- Ties are the common case, not an edge: two or more tied minima at 53-69% of picks; two or more idle
  nodes at 3-22% (SED up to 45%).
- Magnitude vs the audit: the audit reported ~1 pp spread in NQ's weight-4 group; this repro finds
  0.16-0.37 pp there. The audit's "LeastConn and SED are fair" is NOT reproduced: SED is the worst.
- Mechanism (Pick.js NQ ~:878-908, LeastConn ~:716-738, SED ~:797-823): after a pick, `cursor = best + 1`,
  and the next scan takes the FIRST tied (or, in NQ, the first idle) node at or after the cursor. A node
  that sits right after a long run of busy nodes is reached first more often. (Inferred from the code and
  consistent with the sign and the flat interleaved layout; per-node gap distributions were not measured.)

### 1.2 K10 -- failover neighbour double share

/pool keyed run over a ConsistentHashBalancer; attempt 0 fails whenever it lands on backend h; tries 2;
1e5 keys homed on h.

| capacity | neighbour h+1 share of attempt 1 | every other survivor | expected (uniform) |
|----------|----------------------------------|----------------------|--------------------|
| 8        | ~25% (1.75x)                     | 12.3-12.7%           | 14.3%              |
| 64       | 3.06-3.26% (1.93-2.05x)          | ~1.56%               | 1.59%              |

- 100% of attempt-1 dispatches came from the SCAN path, 0% from the re-pick path: a ConsistentHash
  `pick(key)` is deterministic, so all 8 re-picks (Pool.js `REPICK_LIMIT`) return h again.
- Mechanism: the scan start is `imul(key, 0x9e3779b1) % cap` (Pool.js ~:401), derived from the key alone.
  The 1/cap of keys whose start IS h skip forward to h+1, which therefore gets 2/cap.

### 1.3 Failover ignores weight 0

`_scanUntried` (Pool.js ~:136) checks only `isEligible` and the tried list -- never weights.

| scenario                                              | attempt 1 on a weight-0 backend |
|-------------------------------------------------------|---------------------------------|
| ConsistentHash `[1,0,0,0]`, backend 0 fails           | 100%                            |
| ConsistentHash `[1,1,1,1,0,0,0,0]`, backend 0 fails   | 52.6%                           |
| BoundedLoad `[1,0,0,0]`                               | 100%                            |
| SmoothWRR / WeightedRandom / SED / NQ `[1,0,0,0]`     | 100% (only positive node failed) |
| the same unkeyed strategies, `[1,1,1,1,0,0,0,0]`      | 0% (the re-pick finds a positive node) |

So every weighted strategy can dispatch to a REMOVED backend on failover; the keyed ones do it routinely.
This contradicts K8 (weight 0 = removed, fail closed), shipped in phase 1.

## 2. Prior art -- tie-breaking

| system | rule among tied minima | source |
|--------|------------------------|--------|
| Linux IPVS lc / wlc / sed / nq | strict `<`: FIRST in list order wins, every time (nq: first idle in list order) -- a fixed positional bias, stronger than ours | `net/netfilter/ipvs/ip_vs_{lc,wlc,sed,nq}.c` |
| nginx least_conn | detects a tie (`many`), then runs smooth weighted round-robin over the tied peers only -- deterministic, weight-aware | `ngx_http_upstream_least_conn_module.c` |
| HAProxy leastconn (current master) | equal keys share one tree element holding several lists; a server is appended to a RANDOM list and lookups start at a random list -- approximate | `src/lb_fwlc.c` |
| Envoy LEAST_REQUEST, N_CHOICES (default) | samples hosts uniformly at random; ties go to the earlier random sample -- no positional bias | `least_request_lb.cc`, `unweightedHostPickNChoices` |
| **Envoy LEAST_REQUEST, FULL_SCAN** | **strictly lower resets the tie count to 1; an equal score replaces the candidate with probability 1/k -- reservoir sampling, named as such in the source** | `least_request_lb.cc`, `unweightedHostPickFullScan` |
| Finagle P2C | two uniform random draws; ties go to the first draw (random in effect) | `P2CPick.scala` |

No system documents positional bias as a known issue (not found). HAProxy's random lists and nginx's
tie-only round-robin look like deliberate mitigations, but neither source says so.

Reservoir sampling, size 1 (Knuth TAOCP vol. 2 s3.4.2 Algorithm R, attributed to Waterman; Vitter,
"Random Sampling with a Reservoir", ACM TOMS 11(1), 1985): keep `best`; on a strictly better score set
`best = i, ties = 1`; on an equal score `ties++` and replace `best` with probability `1/ties`. After t tied
items, item j survives with probability `(1/j) * prod_{m=j+1..t} (1 - 1/m) = 1/t` -- exactly uniform,
O(1) memory, one random draw per tied item (none for the first of a new minimum).

## 3. Prior art -- failover spreading and weight 0

| system | what attempt n > 0 does | weight / availability on retry |
|--------|-------------------------|--------------------------------|
| Envoy maglev | re-hashes the key with the attempt number (`hash ^= ~0 - attempt + 1`) and probes the table again -- no neighbour walk | per-host table entries; weight-0 handling not confirmed |
| Linux IPVS mh (Maglev) | `ip_vs_mh_get_fallback`: re-hashes with the probe offset as seed, up to table size probes -- a per-key probe sequence | `is_unavailable()` (weight <= 0 or overloaded) is checked on EVERY probe |
| Envoy ring_hash | walks `attempt` entries along the ring; the source warns it may return the same host | weight 0 has no ring entries, so the walk cannot land on it |
| HAProxy consistent hash | a down server's nodes are removed; the ring neighbour inherits its arc (virtual nodes spread it partly) | removal = eweight 0 deletes its nodes |
| Envoy retries | `previous_hosts` predicate rejects already-tried hosts, re-selection bounded by `host_selection_retry_max_attempts` | -- |
| Maglev paper (NSDI 2016) | on removal the table is rebuilt; each backend's own permutation re-claims freed slots, so a removed backend's keys spread over many survivors (secondary sources; the PDF was not readable) | -- |

The neighbour-takes-the-spill effect is textbook for ring hashing; no primary source gives it a name.
The consistent rule across IPVS and Envoy: a retry re-applies the same eligibility AND weight rules as the
first pick, and spreads by re-hashing, not by walking to the next index.

## 4. Options -- K3 (tie-breaking in LeastConn / SED / NQ)

**A. Seeded reservoir pick among tied minima (Envoy FULL_SCAN).** Recommended.
- LeastConn and SED already scan every eligible node, so the change is one compare-and-draw on ties.
- NQ must also choose uniformly among IDLE nodes, so it loses its early return at the first idle node and
  always scans all `cap` nodes (it is already O(cap) worst case). This is the real cost; it must be
  measured, not assumed.
- Needs a `Prng` per balancer: a new optional `seed` constructor argument, defaulting to a fixed seed as
  P2C does, so runs stay reproducible. The cursor (`_cur`) goes away.
- Zero allocation is preserved (the Prng is a pre-allocated state word). Prior art: shipped in Envoy.
- Doc change: "ties rotate / idle nodes take turns" becomes "ties are broken uniformly at random (seeded)".
  Rotation gives exact short-run turns when everything is idle; the reservoir is exact in the long run with
  short-run variance. That is a documented behaviour change (1.1.0 promised rotation, "idle nodes take
  turns"), so it needs a CHANGELOG "Behaviour change" entry and every doc site updated -- but no API or type
  changes, and no caller can depend on WHICH tied node is picked.

**B. Deterministic turn-taking among ties (nginx: smooth WRR over the tied set).** No randomness and exact
short-run turns, but it needs a per-node accumulator array, more code in three hot bodies, and it is
weight-aware among ties (a different rule from A). More moving parts for a quality difference no test here
can show.

**C. Documentation only.** Correct the numbers (SED is the worst case, not NQ; the audit's "~1 pp" is
0.16-0.52 pp here, up to 17% relative inside a weight-1 group) and keep rotation. Zero cost, but it leaves a
measurable, layout-dependent unfairness in three strategies that the library's own fairness anchors would
not show.

## 5. Options -- K10 and weight-0 failover (one fix for both)

**Recommended: replace the linear first-hit scan with ONE weighted choice among untried, eligible,
positive-weight backends.**
- Pass 1 sums the weights of eligible, untried, weight > 0 backends (W). Pass 2 walks the same set and
  returns the backend whose cumulative weight crosses a target in [0, W).
- Target: keyed runs derive it from (key, attempt) through a 32-bit mixer -- stable per key, different per
  attempt (the Envoy maglev / IPVS mh re-hash idea). Unkeyed runs use the Pool's own seeded Prng (or the
  existing rotating counter, mixed).
- Result: spill is weight-proportional over the survivors, with no neighbour preference (K10), and a weight-0
  backend can never be chosen (the weight-0 bug). If W is 0 the run stops failing over and surfaces the last
  error -- the same fail-closed rule K8 applies to the first pick.
- Cost: two O(cap) passes on the COLD failover path only; zero allocation (no array, no closure).
- API: Pool must read weights through the balancer (duck-typed). Proposal: a public read-only
  `weightOf(i)` on the six weighted balancers (CH, BL, WR, SmoothWRR, SED, NQ); a balancer without it counts
  every backend as weight 1 (RoundRobin, P2C, LeastConn, PeakEWMA). New public method = minor, fine for 1.2.0.
- Alternatives considered: (i) the audit's minimal fix -- re-derive the start from a second hash only when it
  lands on h -- fixes the double share for ONE failed node but keeps the linear walk (two adjacent down
  nodes double-load the next one again) and does nothing for weight 0; (ii) IPVS-style rejection probing
  (hash, test, re-hash up to P probes) is uniform but not weight-proportional and can exhaust its probes on a
  small pool with most backends tried; the exact two-pass choice is bounded and simpler to prove.
- The 8 re-picks before the scan stay: BoundedLoad and every load-aware strategy can return a different
  backend on a re-pick, and that is still the preferred path.

## 6. What the implementation must prove (gates)

K3:
- In-repo fairness gate (a seeded, short version of the 1.1 simulation) for LeastConn, SED and NQ: within-
  group spread at noise level for `[1,1,1,1,4,4,4,4]` AND its reverse; must-fail control = the current
  rotating cursor, which must trip it (SED w1 gap 0.52 pp is far above the ~0.05 pp noise floor).
- Exact uniformity of the reservoir itself: a deterministic test with k tied nodes, N picks, chi-square
  bound; plus the "strictly better resets ties" case.
- PerfGate 0 B/op for all three picks; throughput vs 1bc5eec measured at cap 8 / 64 / 1024 (NQ is the one to
  watch). A slowdown bar is a DECIDE below.

K10 + weight 0:
- Spill histogram (the 1.2 table): every survivor within a stated band of its weight share, the neighbour no
  longer ~2x; must-fail control = the old linear scan.
- Weighted spill: survivors with weights 1 and 4 get ~1:4 of the spill.
- Weight 0: zero failover dispatches to weight-0 backends across the 1.3 scenarios; `[1,0,0,0]` with the
  only positive node failing stops after attempt 0 with the original error.
- Stable per key: the same key and attempt pick the same backend while the pool is unchanged.
- Pool perf gate (test:perf:pool) unchanged on the success path; the failover path stays allocation-free.

Both: soak lanes/oracles must still accept the OLD kernels on soak:ab side A (presence-guard every new field,
cross-version test on 1.0.0 / 1.1.0 / 1.1.1 / in-tree -- the phase-1 lesson).

## 7. DECIDE

DECIDED 2026-10-11 (user): (1) A -- seeded reservoir pick; (2) NQ <= 1.25x the 1bc5eec time at cap 64,
cap 8 / 1024 reported, a miss comes back before shipping; (3) weighted choice + public `weightOf(i)`;
(4) stop and surface the last error.

REVISED 2026-10-11 (user), after measurement: the default-on reservoir missed the 1.25x bar in 8 of 9 cap-64
cells (1.40x-8.59x; one draw per tied node -- 63 draws per pick when 64 nodes tie -- and NQ's all-idle cells
cost 2-3 ns before any draw). K3 is now OPT-IN: the default stays the rotating cursor (no slowdown, no
behaviour change; docs carry the corrected bias numbers), and a constructor option `ties: 'random'` gives
exactly uniform ties with a SKIP-based reservoir (Vitter 1985; for a size-1 reservoir the next replacing tie
index is `R = floor(c / u) + 1` after c ties seen, u uniform in (0, 1) (u = x / 2^32, x in [1, 2^32)), so a k-way tie costs about ln k draws
instead of k - 1). The opt-in path's cost is measured and reported, not held to the 1.25x bar.


1. K3: option A (reservoir, recommended), B (deterministic turns) or C (docs only)?
2. K3 throughput bar for NQ losing its early return (proposal: no worse than 1.25x the 1bc5eec time at cap
   64; report cap 8 and 1024 too).
3. K10 + weight 0: the weighted-choice fix with a new public `weightOf(i)` (recommended), or the audit's
   minimal second-hash fix plus a separate weight check?
4. Failover with no positive-weight untried backend left: stop and surface the last error (recommended,
   matches K8), or fall back to an eligible weight-0 backend as today?
