# Research: what goes into 1.1.0, and what we borrow (kernel + API)

**Status:** DECIDED 2026-10-04 -- all recommendations accepted (D1-D8). B1 (the plain fixes: L7, L2, L3, L8,
`setWeights`), B2 (rotating ties, BoundedLoad `minCap`) and B3 (PeakEWMA: Finagle's blend, a decaying pool
mean, timeouts documented in place of the busy-since stamp) and B4 (error codes, stats slab, `describe()`,
`assertConsistent()` -- decisions/0015, with two measured deviations: the shipped `LITE_PICK_*` prefix, and no
per-pick counters) and B5 (Pool `diagnostics_channel` events, decisions/0015 Fork 5) IMPLEMENTED 2026-10-04;
B6-B7 to follow.
**Question:** 1.1.0 collects three lists -- the ROADMAP row (buffer APIs, tie rotation, PeakEWMA busy-since +
decaying mean, observability), the 2026-09-29 audit's Phase 4 kernel items (L2, L3, L4, L7, L8, M5, N4, N5,
H2), and three findings from the Phase 3 soak work. Some are plain fixes. Some are new public API. Some borrow
a technique from a production system. For each: what is the problem, measured on OUR kernel; what do Linux,
IBM, NGINX, HAProxy, Envoy, Finagle and Linkerd do; what do we recommend; what would we NOT copy?

**Short answer:** the fixes are clear and measured (additive Maglev stepping builds the identical table 7.8x
faster at the default M; the sparse-pool fallback is biased 63/37 where it should be 50/50). Of the borrowed
techniques, two are strongly supported by prior art (rotating ties: every L7 proxy spreads ties, only IPVS
does not; Finagle's EWMA blend: ours decays twice), one is our own design with no prior art (a minimum
cap for BoundedLoad -- an opt-in, default off), and one we recommend NOT building (an in-flight age stamp:
nobody does it; timeouts are the production answer). Drain-keeps-slots needs no code: we already have it.

## 2. The plain fixes (no borrowing)

### 2.1 L7 -- build the Maglev table by ADDING the skip, not multiplying
The Maglev permutation of backend b is `offset, offset + skip, offset + 2 skip, ...` (mod M). Our `_build`
computes each entry as `(offset + (j % M) * skip) % M`. Additive stepping keeps a cursor and does
`c += skip; if (c >= M) c -= M` -- the same sequence, without ever forming `j * skip`.

Measured (256 backends, weights 1..8, Node 26, rebuild time; "identical" = every one of the M slots equal):

| M | identical table | today | additive |
|---|---|---|---|
| 257 | yes | 21 us | 19 us |
| 4099 (soak) | yes | 71 us | 42 us |
| 25601 | yes | 502 us | 317 us |
| 46327 / 46351 | yes / yes | 1085 / 1130 us | 848 / 845 us |
| 65537 (library default) | yes | **10,501 us** | **1,345 us** |

Identical tables mean an upgrade moves NO key. The cliff at 65537 is not at the 2^31 product boundary
(46327 and 46351 cost the same), so we do not claim a cause -- only that the multiply path has it and the
additive path does not.

### 2.2 L2 -- the sparse-pool fallback is biased
P2C, PeakEWMA and WeightedRandom draw a random index and retry up to 64 times while it lands on a down node.
After 64 misses they SCAN forward from a random start and take the first up node. A scan favours a node that
sits right after a long run of down nodes: it "owns" that whole run. The kernel's comment calls the scan
"unbiased" -- it is not.

Measured, 200,000 draws, 100 nodes:

| up nodes | P2C draw shares | WeightedRandom (equal weights) |
|---|---|---|
| {0, 1} | 63.5% / 36.5% (should be 50/50) | 63.5% / 36.5% |
| {0, 50} | 50.0% / 50.0% | 50.0% / 50.0% |
| {10, 11, 12, 90} | 24.8 / 23.2 / 23.1 / 28.9% | 24.5 / 23.2 / 23.1 / 29.1% |

Worked example for {0, 1}: 98% of draws miss, so 0.98^64 = 27% of picks reach the scan. A random start lands in
the 98-node gap before node 0 almost always, so the scan returns node 0. 0.73 x 50% + 0.27 x 99% = 63%.
Fix (audit): count the up nodes (`live`, already known), draw `k = nextBelow(live)`, walk to the k-th up node.
Still O(cap), still 0 B/op, still only on the >= 64-miss path; uniform by construction. Test: {0,1} of 100 ->
50/50 +- 1% over 200k picks. (For WeightedRandom the fallback must also respect weights: draw
`u = nextBelow(eligible weight)` and walk the cumulative weights.)

### 2.3 L3 -- ConsistentHash gives up after 64 slots
If the home slot and the next 64 slots all map to down backends, `pick` returns PICK_NONE even though other
backends are up. Linux IPVS's Maglev scheduler has the same problem and a flag for it: `mh-fallback` re-hashes
with an increasing offset across the whole table until it finds an available server
(`ip_vs_mh.c`, `ip_vs_mh_get_fallback`). Our version (audit plan): after the 64-slot window, a cold O(M) sweep
from the slot, first up backend wins. Test: 60 of 64 down -> 0% PICK_NONE.

### 2.4 L8 and comments
`nextBelow` says it is a multiply-shift; it is `Math.floor((x / 2^32) * n)` -- exact, but the wording is wrong.
Fix the comment (and the `_draw` "unbiased" comment, which 2.2 fixes for real).

### 2.5 `setWeights(array)`
ConsistentHash, BoundedLoad and WeightedRandom rebuild a table on every `setWeight(i, w)`. Changing 256 weights
is 256 rebuilds. The soak (and any caller) needs "set all, rebuild once", so today it writes the private
`_weights` and calls `rebuild()` (S14 made that fail closed). A public `setWeights(weights)` -- copy, validate,
one rebuild -- removes the private coupling.

## 3. Ties in LeastConn / SED / NQ (M5) -- borrowed: rotate

**Concept.** LeastConn picks the node with the fewest requests in flight. When several nodes tie for the
fewest -- most visibly when the pool is IDLE -- someone has to win. Our kernel scans from index 0 and keeps the
first, so index 0 wins every tie.

**Worked example on our kernel** (8 nodes, 10,000 requests):

| traffic | today (first index) | prototype: rotating start |
|---|---|---|
| one request at a time (each finishes before the next) | 100% / 0 / 0 / 0 / 0 / 0 / 0 / 0 | 12.5% each |
| three in flight | 33 / 33 / 33 / 0 / 0 / 0 / 0 / 0% | 12.5% each |

At low load a "least-connections" balancer is a "first-server" balancer: one node takes everything, its
caches run hot, the others sit idle and never warm up.

**How others do it** (source pinned to commits, fetched 2026-10-04):
- **Linux IPVS** `lc`, `wlc`, `sed`, `nq`: scan the destination list from the head every time, replace only
  on a strict improvement -- the first wins, exactly like us. `nq` even returns the first idle server
  immediately (`ip_vs_nq.c`: "return the server directly if it is idle"). `lc`/`wlc` soften it a little: the
  overhead is `(active << 8) + inactive` (connections no longer established), so equal ACTIVE counts are
  separated by that second term; `sed`/`nq` use `active + 1` only, so their ties are exact.
- **NGINX** `least_conn`: when several peers tie, a second pass runs smooth weighted round-robin among the tied
  peers only ("if there are multiple peers with the same number of connections, select based on round-robin").
- **HAProxy** `leastconn`: servers sit in a tree keyed by load; every IDLE server has key 0 "so that under low
  loads, it's not always the single server with the highest weight that gets picked"; equal keys are served
  first-in-first-out (a server is re-inserted after each change, so the one just used goes to the back).
- **Envoy** `least_request`: two random choices (a tie keeps the random first), or a full scan with
  RESERVOIR sampling among ties (each tied host 1/N).

Every L7 proxy spreads ties; only the kernel-level IPVS does not.

**Options for us.**
1. **Rotating scan start** (HAProxy-like FIFO): keep a cursor; scan from it; the first tied node at or after
   the cursor wins; the cursor moves past the pick. No random number, no second pass, deterministic, 0 B/op.
   Prototype cost at 256 nodes: 267 ns vs 200 ns (the wrap-around arithmetic; splitting the scan into
   `[cursor, cap)` + `[0, cursor)` should remove most of it -- measure in the burst).
2. Reservoir sampling (Envoy): one random draw per tie -- 256 draws when 256 nodes are idle. Too costly.
3. Weighted round-robin among ties (NGINX): honours weights among ties, but needs a second pass and per-node
   state. For SED/NQ the score already includes the weight; ties are rarer.

**Recommendation: option 1** for LeastConn, SED and NQ. The tie order was documented as unspecified in 1.0.1
(the soak oracle already accepts any tied node, S14), so this is a minor-version change.

## 4. BoundedLoad at low load (N4) -- our own design, opt-in

**Concept.** Consistent hashing with bounded loads (Mirrokni, Thorup, Zadimoghaddam) gives every backend a
capacity `ceil((1 + eps) x (T + 1) / n)` (T = requests in flight, +1 = the incoming one). A key goes to its
home backend unless the home is full, then walks forward to the first backend with room.

**Worked example** (n = 10, eps = 0.25, one key, requests arrive while the earlier ones are still in flight):
- 1st request: T = 0 -> the cap test is skipped -> home.
- 2nd request: T = 1 -> cap = ceil(1.25 x 2 / 10) = ceil(0.25) = 1 -> home already holds 1 -> 1 < 1 fails ->
  it overflows to a neighbour.
- Measured on our kernel: 5 concurrent requests for ONE key landed on 5 different backends (6, 4, 1, 3, 0).

At low load "bounded loads" means "no affinity at all for concurrent requests" -- exactly the opposite of what
a caller who chose consistent hashing wants (warm caches per key).

**How others do it.**
- **HAProxy** `hash-balance-factor` (`lb_chash.c`): a global budget `ceil((served + 1) x F / 100)` split by
  weight, minimum 1, strict test `served < slots` -- the SAME as ours: the 2nd concurrent same-key request
  always leaves home.
- **Envoy** `hash_balance_factor`: `slots = max(ceil(total_slots x weight), 1)` but accepts while
  `active <= slots` -- so a home keeps up to 2 concurrent requests. A de facto floor of 2, from a `<=`, not a
  documented decision. Envoy also probes in a hash-seeded random order, not a forward walk.
- **Vimeo (Rodland, 2016) and the Google blog (2017)**: neither mentions a minimum capacity.

No implementation offers an explicit knob. **Recommendation:** an opt-in `minCap` option on
`BoundedLoadBalancer` -- `cap = max(minCap, ceil(...))` -- default 0, which keeps today's (and HAProxy's,
and the paper's) behaviour exactly. Document it as OUR extension, with the trade-off: a larger `minCap`
keeps more concurrent same-key requests at home, at the price of a looser bound at low load (with
`minCap = 2`, a backend can hold 2 while the average is 0.1). We would NOT copy Envoy's silent `<=`.

## 5. PeakEWMA -- borrowed: Finagle's blend; a decaying mean; no age stamp

**Concept.** PeakEWMA ("peak exponentially weighted moving average", Finagle) keeps a per-node latency
estimate that jumps UP at once on a slow response (the peak) and eases back down over a time constant tau.
Cost = estimate x (requests in flight + 1). Two random candidates, the cheaper wins.

What Finagle, tower (Rust) and Linkerd do -- all three, from source:
- cost = estimate x (pending + 1);
- update: `w = exp(-dt / tau)`; if the sample is above the stored value it REPLACES it; else
  `value = value x w + sample x (1 - w)`;
- the estimate also decays toward 0 every time it is READ (Finagle calls `observe(0)` on read; tower decays in
  `load()`). Ours does the same (`ewmaAt` is a pure decayed read).
- Linkerd's published test (11 backends, one slowed to 2 s for 30 s, 1 s timeout): success rate ~95% round
  robin, ~99% least-loaded, ~99.9% Peak EWMA.

### 5.1 L4 -- our blend decays twice
Ours: `e = value x w; value = (sample > e) ? sample : e + (sample - e) x (1 - w)`, which expands to
`value x w^2 + sample x (1 - w)`. Finagle/tower: `value x w + sample x (1 - w)`.

Worked example: value 10 ms, one tau since the last sample (w = 0.368), new sample 5 ms.
- Finagle: 10 x 0.368 + 5 x 0.632 = **6.84 ms**.
- Ours: e = 3.68; 3.68 + (5 - 3.68) x 0.632 = **4.51 ms** -- we forget a slow period faster than designed.
The peak comparison differs too (ours compares with the decayed value, Finagle with the stored one).
**Recommendation:** adopt Finagle's formula exactly, with a unit test pinning this example (D3).

### 5.2 The price of a node with no sample yet
- **Finagle:** an unsampled node with nothing in flight costs 0 (most attractive -- it gets probed); with a
  request in flight and still no sample it costs a huge Penalty, so it gets ONE probe at a time.
- **tower:** seeds every node with a caller-chosen default RTT (Linkerd passes 30 ms); it decays like any sample.
- **Linkerd's newest crate:** an unseeded node costs INFINITY.
- **Ours (1.0.1):** idle -> 0 (like Finagle); busy -> (inflight + 1) x the LIFETIME mean of all samples ever seen.

The lifetime mean is the weak spot: a slow first hour keeps pricing new nodes high forever, a fast first hour
keeps them cheap forever. **Options (D4):** (a) a DECAYING pool mean (the ROADMAP item: an EWMA over all
samples with the same tau) -- keeps our faster ramp-up; (b) Finagle's penalty while busy -- safest against a
"black hole" node (fails fast, looks cheap), slowest ramp-up; (c) a caller-chosen default RTT (tower).
**Recommendation: (a)**, with the 1.0.1 failure penalty (a thrown attempt records `max(elapsed,
failurePenaltyNs)`) still guarding the black hole -- which is exactly how Linkerd's newest code does it
(failures record a penalized RTT through the peak rule).

### 5.3 N5 -- a hung node with no sample (the busy-since stamp): do not build
The ROADMAP planned a "busy-since" stamp: remember when a node went from 0 to 1 in flight, and price it by
that age so a node whose requests never return gets expensive even before any sample.
- **Nobody does this.** Finagle, tower and Linkerd stamp the send time but read it only when the request
  ends. Envoy has no latency term at all; gRPC's weighted round robin gives a non-reporting backend the
  AVERAGE weight. The production answer is the TIMEOUT: a timed-out request records its elapsed time as a
  peak sample (tower records on drop; our Pool records `max(elapsed, failurePenaltyNs)` on a throw).
- Ours already goes further than all of them for SAMPLED nodes: the 1.0.1 busy floor prices a busy node at
  no less than the time since its last sample.
- A stamp needs the balancer to SEE the 0 -> 1 transition; `inflight` is caller-owned and read-only to
  PeakEWMA, so it would need a new `note()`-style call on every dispatch -- new API for a case nobody else
  handles.
**Recommendation (D5):** do not build it. Document "set a timeout" for Pool users (Pool already turns a
timeout into a penalized sample), and keep the busy floor.

## 6. Drain versus remove (IPVS `mh`) -- we already have it

**Concept.** Taking a backend out of a hash table two ways: DRAIN (stop sending it new work, keep its slots so
nothing else moves) and REMOVE (rebuild the table without it; some other keys move).
- **Linux IPVS `mh`:** the table is built from `last_weight`, the last NON-zero weight. Setting weight 0 keeps
  the server's slots; lookups check the live weight and, with `mh-fallback`, re-hash to another server.
  Deleting the server rebuilds.
- **Envoy** Maglev/ring hash and the **Maglev paper:** rebuild from the healthy set (minimal disruption, not zero).
- **lite-pick today:** `setEligible(i, false)` keeps the table and probes past the down slot -- S14 measured
  0 other keys moved in 20,000 events. `setWeight(i, 0)` rebuilds -- 2.2% of other keys move (median).

So IPVS's "drain" is our `setEligible(false)`, and its "remove" is our `setWeight(0)`. **Recommendation (D6):**
no code; a RECIPES/GUIDE section "drain vs remove" with these numbers. (L3 is our `mh-fallback`.)

## 7. Observability -- new API, measured

### 7.1 Counters
Prior art: IPVS per-service stats (fixed u64 slots; 32-bit counters wrapped and a 64-bit attribute had to be
added later), Envoy (64-bit counters, names resolved to slots up front, caller-owned scopes), HAProxy
`show stat` (fixed columns, new ones only appended; `lbtot` = times a server was selected).
Measured (50M increments): `Uint32Array` 0.41 ns (wraps after 2^32 -- ~7 minutes at 10M/s), `Float64Array`
0.73 ns (exact to 2^53 -- ~104 days at 1e9/s), `BigUint64Array` 13 ns and ALLOCATES.
**Proposal:** a caller-supplied `Float64Array` stats slab, frozen index constants (`STAT_PICKS`,
`STAT_FALLBACK_SCANS`, `STAT_PICK_NONE`, `STAT_REBUILDS`, ...), only ever appended, never reset (readers take
deltas). To keep the hot body small, a balancer without a slab writes to a shared scratch slab
unconditionally -- no branch.

### 7.2 Hooks for the Pool: `node:diagnostics_channel`
Measured on Node 22.23 and 26.8 (`--max-semi-space-size=1`, 10M calls):

| | Node 22 | Node 26 |
|---|---|---|
| `if (ch.hasSubscribers) ch.publish(...)`, nobody listening | 0.44 ns, 0 GC | 0.31 ns, 0 GC |
| guarded, one subscriber, ONE reused message object | 5.73 ns, 0 GC | 5.61 ns, 0 GC |
| guarded, one subscriber, a fresh object per call | 8.70 ns, 315 GC | 8.71 ns, 458 GC |

Unguarded with nobody listening, the object is still built (it is the argument) and only V8's optimizer
sometimes removes it (the agent measured 382-534 scavenges/10M in the lower tiers). So: always guard, reuse
one message object, subscribers copy what they need synchronously. Naming: module prefix (Node's rule;
undici uses `undici:request:create`) -> `lite-pick:pool:dispatch`, `lite-pick:pool:settle`.
`TracingChannel` is stable only from Node 26.8 and its combined `hasSubscribers` is missing on Node 18, so
plain channels. Browsers have no `diagnostics_channel`: load it optionally (`process.getBuiltinModule` where
present), no channel otherwise -- Pool stays browser-safe. Never inside `pick()`.

### 7.3 Error codes
Node: "`error.message` ... may be changed in any versions. Use `error.code`"; codes are stable. Libraries use
their own prefix (`UND_ERR_*`, `FST_ERR_*`). **Proposal:** keep throwing `TypeError`/`RangeError`, add
`code = 'LITE_PICK_ERR_*'` (not `ERR_LITE_PICK_*`, which reads like Node's own), and treat codes as semver API.

### 7.4 `describe()`
Precedent: Envoy admin `/clusters`, HAProxy `show stat typed`, Finagle's `loadbalancer/*` gauges. **Proposal:**
a cold, allocation-allowed `describe()` snapshot (live, weights, table size, counters), plus
`[Symbol.for('nodejs.util.inspect.custom')]` -- works in Node without an import, ignored in browsers. H2's
`assertConsistent()` (recount `live`, O(cap), opt-in) fits here.

## 8. Decisions needed

1. **D1 ties:** rotating scan start for LeastConn/SED/NQ (recommended), vs reservoir, vs NGINX-style WRR?
2. **D2 BoundedLoad:** add opt-in `minCap` (default 0, documented as our extension)? Or leave N4 as documented
   behaviour only?
3. **D3 PeakEWMA blend:** adopt Finagle's formula exactly (recommended; changes the numbers, pinned by a test)?
4. **D4 unsampled-busy price:** decaying pool mean (recommended) vs Finagle penalty vs default RTT?
5. **D5 busy-since stamp:** drop it in favour of documented timeouts (recommended)?
6. **D6 drain:** document `setEligible(false)` = drain and `setWeight(0)` = remove (recommended), no new API?
7. **D7 observability:** Float64Array stats slab + `LITE_PICK_ERR_*` codes + `describe()` + guarded
   `diagnostics_channel` in /pool only -- all four, or a subset for 1.1.0?
8. **D8 buffer APIs:** design them in their own short note at the start of that burst (names, buffer layout)?

**Proposed burst order** (each one is a commit you review): (B1) plain fixes L7, L2, L3, L8 + `setWeights`;
(B2) ties + `minCap`; (B3) PeakEWMA blend + decaying mean + docs for timeouts; (B4) errors + counters +
`describe()`/`assertConsistent()`; (B5) Pool `diagnostics_channel`; (B6) buffer APIs (+ the `recordRtt`
isolation investigation); (B7) docs (drain vs remove, the lite-logn seam) and release. The soak oracles from
Phase 3 already accept rotated ties, so the soak stays green through B2.

## What we would NOT copy
- IPVS's first-index ties (the hotspot measured above).
- Envoy's implicit `<=` capacity (a silent floor of 2; ours would be explicit and default off).
- A lifetime mean anywhere (nobody uses one; all decay by wall-clock time).
- An in-flight age penalty (no prior art; timeouts do the job).
- `TracingChannel.tracePromise` in the Pool (wraps and allocates per request).
