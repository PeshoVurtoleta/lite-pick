# Research: zero-box buffer APIs for 1.1.0 (B6) -- names, slot layout, and the open recordRtt item

**Status:** DECIDED 2026-10-05 -- E1-E6 accepted as recommended. IMPLEMENTED 2026-10-05 (B6; decisions/0016).
All numbers come from a prototype measured on the real kernel, not from the literature.
**Question:** `pick(now)`, `recordRtt(i, sampleNs, now)` and `pick(keyHash)` take numbers that are often too
large (a nanosecond clock, a 32-bit hash) or fractional (an rtt from `performance.now()`) to travel as V8 small
integers, so V8 boxes them into a 16-byte heap object at the call. What should the boxing-free variants be
called, where do the values live, what do they promise -- and is the open "recordRtt in isolation" allocation
item related?

**Short answer:** add `pickFrom(buf, i)` (PeakEWMA, ConsistentHash, BoundedLoad) and
`recordRttFrom(endpoint, buf, i)` (PeakEWMA), following the suite's existing `addFrom` / `searchFrom`
convention: the caller writes the number into its own typed-array slot and passes the slot. Measured: 0 B/op
on every path, on Node 22 and 26, even with V8 inlining switched off. Two extras fall out of the investigation:
(1) the open "recordRtt in isolation" item now has an established root cause, and B3 already removed it;
(2) the PRNG itself boxes when V8 does not inline it -- a two-site fix keeps the random streams bit-identical.

---

## 1. Concepts, in plain words

- **Small integer (Smi) vs HeapNumber.** V8 passes a number between functions as one machine word. If the value
  is an integer that fits the "small integer" range it travels as-is. Anything else -- a fraction, or an integer
  outside the range -- must be put in a separate 16-byte heap object (a *HeapNumber*) first. That is "boxing".
  The range depends on the build: on stock 64-bit Node (no pointer compression; this machine reports
  `v8_enable_pointer_compression: 0`) it is [-2^31, 2^31); on Chrome / Electron (pointer-compressed) it is
  [-2^30, 2^30).
- **Where boxing happens.** Inside one optimized function a double lives in a CPU register and never boxes. It
  boxes when it crosses a boundary that needs a tagged word: a call V8 did not inline, a value saved across an
  `await`, or -- the subtle one -- a merge point (`cond ? a : b`) where one input is already a tagged word.
- **What our numbers look like in real use.** A nanosecond clock is ~1.7e18 (never a Smi). A 32-bit hash is
  >= 2^31 half the time (not a Smi on Node, and >= 2^30 three quarters of the time on Chrome). An rtt computed
  from `performance.now()` is fractional. So the plain-argument APIs box on every call V8 does not inline.
- **A typed-array slot is the only unboxed memory a caller can hand over.** JavaScript has no value types. A
  `Float64Array` stores raw doubles; reading `buf[i]` inside the kernel puts the value straight into a register.

## 2. How others solve it

- **Inside this suite (the convention to follow).** lite-sketch `addFrom(buf, i)` / `addHashedFrom(buf, i)`,
  lite-adaptive `addFrom(buf, i)` / `advanceFrom(buf, i)`, lite-logn `setFrom(src, i)` / `searchFrom(src, i)`.
  Each is the "zero-box sibling" of the plain method: same semantics, the value read INSIDE from a caller-owned
  typed array, multi-value tuples in ADJACENT slots (`[key, count]` at `buf[i], buf[i+1]`; `[hi, lo, count]` at
  `buf[i..i+2]`). lite-logn's note even says `searchFrom` exists because lite-pick will call it per pick.
- **JavaScript graphics libraries.** three.js `Vector3.fromArray(array, offset)` / `toArray(array, offset)` and
  gl-matrix's `out`-parameter style (`vec3.add(out, a, b)`) exist for the same reason: keep numbers in typed
  arrays so a hot loop allocates nothing.
- **Java (the IBM / OpenJDK answer).** Java boxes `Integer` / `Double` the same way. Its answers are primitive
  specialisations (`IntStream`, `DoubleUnaryOperator`, the Trove / fastutil collections), escape analysis in the
  JIT (HotSpot C2, OpenJ9) that removes boxes the JIT can prove local, and -- the long-term fix -- Project
  Valhalla's value classes. JavaScript has neither value types nor guaranteed escape analysis across a call,
  which is why the slot pattern is the one tool that works on every engine and tier.
- **Linux.** Not applicable as such (C values are never boxed), but the kernel's habit is the same one: pass a
  pointer to caller-owned memory (`struct` out-parameters, ring buffers) rather than allocate per call.

## 3. What boxes today -- measured

Prototype vs HEAD (`076157e`), darwin arm64, 256 nodes, realistic magnitudes (clock 1.7e18, fractional rtt,
keys >= 2^31). B/op from scavenge counts with the young generation pinned at 1 MB (`--trace-gc`, 4M ops).
"No-inline" runs with `--max-inlined-bytecode-size=0`, the worst case: a caller V8 refuses to inline into.

| call | HEAD default | HEAD no-inline | proposal default | proposal no-inline |
|---|---|---|---|---|
| PeakEWMA `pick(now)` | 16 | 32 | 0 * | 32 -> 16 ** |
| PeakEWMA `pickFrom(buf, i)` | -- | -- | 0 | 0 ** |
| PeakEWMA `recordRtt(i, s, now)` | 16 | 24 | 16 | 24 |
| PeakEWMA `recordRttFrom(i, buf, j)` | -- | -- | 0 | 0 |
| ConsistentHash `pick(key)` | 0-6 *** | 16 | 0 * | 16 |
| ConsistentHash `pickFrom(buf, i)` | -- | -- | 0 | 0 |
| P2C `pick()` | 0 | 16 | 0 | 0 ** |
| WeightedRandom `pick()` | 0 | 16 | 0 | 0 ** |

Node 22.23 gives the same table (within 0.5 B/op). `*` the plain method becomes a 3-line wrapper that V8 now
inlines into the caller, so its argument never crosses a call -- welcome but NOT a promise (it depends on the
caller being inlinable). `**` with the PRNG fix (section 5). `***` HEAD's keyed `pick` depends on whether V8
inlines it: the perf gate's report-only lanes print 0 on one run and 24 scavenges on the next. The `From`
variants do not depend on inlining at all -- that is the point.

Time (ns/op, 256 nodes, A/B in one session): `pickFrom` = `pick` for both strategies; `recordRttFrom` 9.6
vs `recordRtt` 8.6 (one more slot read + the buffer check); no change to any other strategy's pick (WR 39.3 /
39.6, P2C 56.4 / 55.8, PeakEWMA 83.5 / 82.7, CH 6.6 / 6.6, BL 13.4 / 13.4).

## 4. The proposal

### 4.1 API (E1, E2)

```js
// PeakEWMA -- the clock in a Float64Array slot
const t = new Float64Array(1);
t[0] = clockNs();                    // write the number, never pass it
const i = lb.pickFrom(t, 0);         // == lb.pick(t[0]), 0 B/op

// PeakEWMA feedback -- [sampleNs, now] in adjacent slots (the order of recordRtt's arguments)
const fb = new Float64Array(2);
fb[0] = doneNs - startNs; fb[1] = doneNs;
lb.recordRttFrom(i, fb, 0);          // == lb.recordRtt(i, fb[0], fb[1]), 0 B/op

// ConsistentHash / BoundedLoad -- the key in a Uint32Array slot
const k = new Uint32Array(1);
k[0] = fnv1a(userId);
const j = ch.pickFrom(k, 0);         // == ch.pick(k[0]), 0 B/op
```

- `pickFrom(buf, i)` on `PeakEwmaBalancer`, `ConsistentHashBalancer` and (inherited) `BoundedLoadBalancer`.
  Strategies whose `pick()` takes no argument get nothing -- they have nothing to box.
- `recordRttFrom(endpoint, buf, i)` on `PeakEwmaBalancer`: `sampleNs = buf[i]`, `now = buf[i + 1]`.
- Any typed array works for keys (`>>> 0` normalizes the slot exactly as `pick(key)` does); a `Uint32Array`
  is what a 32-bit hash naturally is. The clock and rtt slots should be a `Float64Array` (an integer typed
  array would truncate them).

### 4.2 Contracts (E3, E4)

- **`pickFrom` keeps `pick`'s never-throw contract for every value.** An index past the end reads `undefined`,
  which behaves exactly like `pick(NaN)`: key 0 for ConsistentHash / BoundedLoad, P2C-random selection for
  PeakEWMA (both documented today). No type check on the hot path: a buffer that is not indexable at all
  (`null`, `undefined`) throws the engine's TypeError -- a programming error, documented, not validated per pick.
  The suite's other `From` methods validate and throw, but none of them is a never-throw pick path; a check
  here would add bytes to the hottest body we have.
- **`recordRttFrom` validates like `recordRtt` (warm path):** `LITE_PICK_INDEX` for a bad endpoint,
  `LITE_PICK_ARRAY` for anything but a `Float64Array` with both slots `i` and `i + 1` in bounds,
  `LITE_PICK_ARGUMENT` for a non-finite or negative sample / non-finite now -- all before any write.

### 4.3 Implementation shape (one body, no duplication)

A `From` method must never hand its double to a function V8 might not inline -- that would box again. So the
shared body reads from a slot:

- PeakEWMA: the current `pick(now)` body becomes `_pickAt(buf, i)` (its first line is `const now = buf[i]`).
  `pickFrom(buf, i)` calls it directly; `pick(now)` writes `now` into a balancer-owned `Float64Array(2)` and
  calls it with that. Same for `recordRtt` / `recordRttFrom` around `_recordAt(endpoint, buf, i)`.
- ConsistentHash / BoundedLoad: the key is reduced to its slot FIRST -- `(key >>> 0) % M` is always a small
  integer -- so the shared body `_pickSlot(slot)` never sees the large value. `pick(key)` and `pickFrom(buf, i)`
  are one line each.
- The balancer-owned scratch slots are per instance (no shared module state), allocated once in the constructor.

## 5. Finding: the PRNG boxes when it is not inlined (E5)

With inlining off, `pickFrom` still showed 16 B/op. A sampling heap profile pointed nowhere inside the kernel,
so the culprit was a value crossing a call: `Prng.next()` returns a uint32 that is >= 2^31 half the time, and
`nextBelow(n)` calls `next()`. P2C draws twice per pick: on average one box. WeightedRandom calls `next()`
directly for its uniform draw. It never shows in the default mode because `next()` is tiny and always inlined
(which is why the perf gates pass), but it is the same zero-box law as section 1.

**Fix:** `nextBelow` runs the xorshift step itself instead of calling `next()`, and WeightedRandom's two uniform
draws do the same five lines inline. Verified bit-identical: `next` / `nextBelow` streams over 1e6 steps and the
WeightedRandom pick sequence over 1e6 picks match HEAD exactly, so every seeded test, benchmark and soak
calibration is unaffected. Result in the table above: P2C, WeightedRandom and PeakEWMA reach 0 B/op even with
inlining off; no ns change.

## 6. The open "recordRtt in isolation" item: root cause established, already fixed

PerfGate has carried a FINDINGS note since 1.0.1: the `recordRtt(now & MASK, now % 500000, now)` lane allocated
a little when run ALONE (8N:2 / 16N:4 / 32N:9), vanished with `--no-maglev` or when another lane ran first, and
"no single mechanism has been proven". Measured now, the lane run alone through lite-perf-gate's own `measure`,
30 windows each:

| kernel | windows that allocated |
|---|---|
| 1.1.0 B2 (`9872abe`, before B3) | 4 / 30, then 5 / 30 on a second run |
| the same kernel with ONLY the blend line changed (see below) | 0 / 30 |
| HEAD (after B3) | 0 / 30, 0 / 30 |

The line: `this._ewma[i] = sampleNs > e ? sampleNs : e + (sampleNs - e) * (1 - w)`. The `? :` merges
`sampleNs` -- a tagged argument -- with a freshly computed double. Maglev (V8's mid tier) gives such a merge a
tagged representation, so whenever the blend branch is taken the double is boxed. That explains every
observation: value-dependent (only when a sample falls below the estimate -- the `% 500000` saw-tooth does
that regularly, the `& 0x7ffff` mask pattern much less), only in isolation (it lives exactly as long as the
Maglev code does; other lanes running first change when TurboFan replaces it), gone with `--no-maglev`
(TurboFan picks a float64 representation for the merge). It is the same mechanism B3's perf gate caught in the
new pool mean. B3 rewrote the blend as an `if` / `else` with two stores (no merge), which is why it is gone.

**Proposal:** turn the report-only "OPEN" lane into a gated lane (it reads 0 now, so a regression fails), and
replace the FINDINGS note with this explanation and a pointer here.

## 7. What we would NOT do (E6)

- **Pool does not switch to `pickFrom`.** Pool's `now` lives across an `await` in an async function, and V8
  stores such values tagged, so it is boxed before Pool could hand it to `pickFrom`; `run` allocates promises
  anyway and was never 0 B/op. A caller who needs the 0 B/op path drives the kernel directly.
- **No BigInt clock** (`process.hrtime.bigint()`): every BigInt is a heap object; it is the opposite of the goal.
- **No change to `pick(now)` / `recordRtt` signatures.** They stay, and stay correct; the `From` variants are
  additive (minor version).
- **WeightedRandom dynamic weights via lite-logn `searchFrom`** stay a documented seam (B7), not code.

## 8. Gates that come with it

- PerfGate: new GATED lanes at REALISTIC magnitudes -- `pickFrom` with a 1.7e15 clock, `recordRttFrom` with a
  fractional sample, CH / BL `pickFrom` with keys >= 2^31 -- each `maxScavenges: 0`. The plain-argument
  report-only lanes stay (they document what the plain methods still cost).
- The isolation lane becomes gated (section 6).
- A small extra run of those lanes with `--max-inlined-bytecode-size=0`, so the "0 B/op even when not
  inlined" claim is gated too, not just measured once.
- Unit tests: `pickFrom` == `pick` and `recordRttFrom` == `recordRtt` on identical inputs (same picks, same
  `_ewma` / `_stamp` / `_samp` bytes), the never-throw contract for out-of-range indexes, and every
  `recordRttFrom` rejection with its code and no write.

## 9. Decisions

1. **E1 names:** `pickFrom(buf, i)` and `recordRttFrom(endpoint, buf, i)` -- the suite's `xxxFrom` convention
   (recommended)?
2. **E2 layout:** `recordRttFrom` reads `[sampleNs, now]` at `buf[i], buf[i+1]` -- recordRtt's argument order
   (recommended), not `[now, sampleNs]` or two buffers?
3. **E3 `pickFrom` contract:** never throws for any value or index, no per-pick type check, a non-indexable
   buffer is a documented programming error (recommended) -- or validate like lite-sketch and throw?
4. **E4 `recordRttFrom` validation:** as recordRtt plus `LITE_PICK_ARRAY` for a bad buffer / slots
   (recommended)?
5. **E5 PRNG fix:** self-contained `nextBelow` + inline WeightedRandom draws, streams bit-identical
   (recommended)?
6. **E6 scope:** Pool unchanged; no BigInt; plain methods unchanged (recommended)?
